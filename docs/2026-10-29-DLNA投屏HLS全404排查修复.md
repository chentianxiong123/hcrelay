# HomeCast Relay：DLNA 投屏 HLS 全 404 排查与修复记录

## 背景

用手机当 DLNA 中继（接收 App 投屏 → 转推给真实电视），投 B站/百度/抖音时电视一直转圈不出画面。前面已经把「设备发现」「严格客户端识别」都修好了，百度 App 已经能在列表里看到 `HomeCast Relay`，但真正推流还是失败。

这次记录的是最后一块：HLS 播放列表里的分片全部 404。

## 问题现象

电视（HiDMR，192.168.31.3）能识别到我们的服务、会去拉 m3u8，但拉分片时全是 404：

```
[http] GET /m/0001355.ts from 192.168.31.3 -> 404
[http] GET /m/0001356.ts from 192.168.31.3 -> 404
```

服务端日志里 Upstream 全是 200，说明**上游是好的**，是我们自己的路由对不上。

## 排查过程

### 1. 先确认电视本身能播 HLS

一开始怀疑是 HiDMR 不支持 HLS。用它的 UA 去抓请求：

```
Lavf/56.40.101
```

FFmpeg 的 Lavf 库 —— 说明电视主动解析了 m3u8，并且**自己在按分片名请求**（`0001355.ts`）。它把相对路径解析到了我们的 `/m/` 根下，而不是我们的会话路径。

结论：电视没问题，是我们的 m3u8 里塞了不能直接用的相对路径。

### 2. 看上游 m3u8 长啥样

```bash
curl -s -H "Referer: https://www.bilibili.com/" \
  "https://s3.bfllvip.com/video/jijieyueyu/b2cea4957d6e/index.m3u8"
```

```m3u8
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:2
#EXT-X-PLAYLIST-TYPE:VOD
#EXTINF:1.08,
0000000.ts
#EXTINF:1,
0000001.ts
```

分片是**相对文件名**。上游 Content-Type 是 `application/vnd.apple.mpegurl`。

### 3. 验证「丢目录」这个猜想

原来的 `rewritePlaylist` 把分片改成：

```go
lines[i] = segBase + strings.TrimPrefix(u.Path, "/")
```

`segBase` 是 `http://ip:8080/m/<id>/seg/`，`u.Path` 是 `/video/jijieyueyu/b2cea4957d6e/0000000.ts`，拼出来带目录，是对的。

但老的 `hls` 模式不是这么干的，它是：

```go
base := up.Scheme + "://" + up.Host
segURL := base + "/" + segName   // ← 目录没了
```

试一下就知道：

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  "https://s3.bfllvip.com/0000000.ts"      # 404
curl -s -o /dev/null -w "%{http_code}\n" \
  "https://s3.bfllvip.com/video/jijieyueyu/b2cea4957d6e/0000000.ts"  # 200
```

**同一个分片，差一个目录，结果天差地别。** 相对路径解析必须用 `url.ResolveReference`，不能手拼字符串。

### 4. 顺带发现抖音的坑

抖音给的 m3u8 URL **不以 `.m3u8` 结尾**，靠后缀判断会漏。只能靠响应的 `Content-Type`。

但推给电视的 DIDL `protocolInfo` 又需要在**推之前**就知道类型 —— 这是个时序问题。

## 解决方案

### 核心：分片用 base64url 编码绝对 URL

不手工拼路径了，直接把上游**绝对 URL** 用 base64url 编码后当路径：

```go
func hlsSegPath(sessionID, absURL string) string {
	return "/m/" + sessionID + "/seg/" + base64.RawURLEncoding.EncodeToString([]byte(absURL))
}
```

重写后的播放列表长这样：

```m3u8
#EXTINF:1.08,
http://192.168.31.204:8080/m/1793269184506333324/seg/aHR0cHM6Ly9zMy5iZmxsdmlwLmNvbS92aWRlby9qaWppZXl1ZXl1L2IyY2VhNDk1N2Q2ZS8wMDAwMDAwLnRz
```

解码回来正好是 `https://s3.bfllvip.com/video/jijieyueyu/b2cea4957d6e/0000000.ts`，目录完整。

好处是**不用自己拼路径**，相对路径、绝对路径、带 query 的 URL 全都天然正确。

### 内容类型探测（解决抖音）

在 relay 里加 `probeMime`，推给电视之前先探一下上游真实 Content-Type：

```go
req.Header.Set("Range", "bytes=0-1023")  // 只读头部
```

另外还读前 16 字节看是不是以 `#EXTM3U` 开头 —— 有些 CDN 对 Range 返回 200 + `video/mp2t`，但实际内容是 m3u8 文本，得靠内容判断。

探测到是 HLS，就把 mime 改成 `application/vnd.apple.mpegurl`，推给电视的 DIDL 就正确了。

### 补齐各种标签里的 URI

抖音常用 fMP4 + AES 加密，只重写分片行是不够的：

| 标签 | 用途 | 处理 |
|---|---|---|
| `#EXT-X-MAP:URI="init.mp4"` | fMP4 初始化段 | 重写成代理路径 |
| `#EXT-X-KEY:URI="key.bin"` | AES 加密密钥 | 重写成代理路径 |
| `#EXT-X-MEDIA:URI="..."` | 音轨/字幕 | 重写成代理路径 |
| master playlist 里的 `.m3u8` | 多码率子列表 | 走 `/pl/` 路径，递归重写 |

### 顺手把模式选择删了

这次最大的 UX 改动 —— **目标用户是我妈，不需要理解「直连代理 / 重封装 / HLS 修复」是什么**。

所以：

- UI 上的三选一模式卡：**删掉**
- 后端统一 `mode=auto`，按上游流自动决定
- proxy 模式内部自己会按 Content-Type 判断要不要走 HLS 分支

现在妈妈只需要：打开 App → 选电视 → 用 B站/百度投屏 → 选 HomeCast Relay。完事。

## 坑与教训

1. **相对路径解析永远用 `url.ResolveReference`，别手拼。** 我就因为手拼丢了一次目录，排查绕了一大圈。

2. **URL 后缀不可靠。** 抖音的 m3u8 URL 不带后缀，必须看响应 `Content-Type`。而且 CDN 可能对 Range 返回错误类型的内容，得 peek 一下 body。

3. **HLS 不只是「分片行」。** fMP4 的 `EXT-X-MAP`、加密的 `EXT-X-KEY`、master playlist 的子列表，都是 URI 引用，漏一个就播不了。

4. **base64url 编码绝对 URL 是个好用的偷懒法。** 不用设计路径映射表，不用担心 query 里的特殊字符，不用担心目录层级。

5. **给普通人用的东西，选项越少越好。** 「直连代理/重封装/HLS 修复」这三个词对我妈来说就是三个障碍。全自动才是对的。
