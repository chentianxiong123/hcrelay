# HomeCast Relay 排查实录：B站投屏长时间播放后音画变慢/爆破音的真相

> **一句话结论**：B站 CDN 的流 URL 是**签名 URL**，query 里带 `deadline`（unix 秒时间戳），**约 30 分钟到期**。到期后 CDN 返回 **403**，投屏播放器（或我们的中继）还在拿旧 URL 拉分片，于是电视拉不到新数据，出现**变卡、变慢、爆破音**，而且**一直卡不恢复**（URL 已永久失效）。
>
> 这解释了为什么**只有 B站长视频**（15/20/30 分钟）才触发：B站的 URL 有效期刚好卡在 30 分钟，百度/抖音/盗版站的 URL 要么不过期、要么有效期更长。

---

## 一、背景

家里老人用手机（百度/B站/抖音 App）**DLNA 投屏**到电视（HiDMR）看视频。直接投屏时有个顽固毛病：**B站长视频播放一段时间后（约 15~30 分钟），音画一起变慢、变卡、出现爆破音，而且一直卡不恢复**。短视频、百度、抖音、盗版站都没这问题。

为了修这个，我做了个**中继服务 HomeCast Relay**：手机（或一台 Linux 小主机）作为"DLNA 接收端 + 转发端"，把 App 投屏来的流**重新包装后转发给真实电视**，在中间做各种"整流"。项目用 **Go** 实现（零 ffmpeg、零转码），wails3 打包 Android APK。

> 项目地址：https://github.com/chentianxiong123/hcrelay

本文记录我从头到尾的**全部排查折腾**，以及最终**真相大白**的过程。弯路很多，都记下来，值钱的恰恰是这些弯路。

---

## 二、问题现象（用户精确描述，反复确认）

1. 只有 **B站长视频**（15 / 20 / 30 分钟）才触发；百度 / 抖音 / 盗版站都**不会**
2. 流**前期非常流畅**，播到某个时间点**突然**出问题
3. **突然爆破音**（音频"啪"地爆掉）+ **画面卡顿但继续播放**（不是定格）
4. 变卡变慢后**一直能放，但一直卡、一直慢，不恢复**
5. **不是**渐进式越播越慢，是**突发、破坏性**的；**不是**音画错位（音视频不同步），是**一起**变慢

## 三、排查过程（按时间顺序，弯路全记录）

### 3.1 第一阶段：DLNA 分工与初步架构

先搞清楚 DLNA 投屏的原理分工：

| 角色 | 说明 |
|------|------|
| **App（控制点）** | 百度/B站/抖音 App，发现设备、发起投屏 |
| **DLNA 接收端（我们）** | 我们的中继，作为 MediaRenderer 被 App 发现 |
| **电视（目标渲染器）** | HiDMR 电视，真正播放媒体 |

中继链路：**App →（SSDP 发现 + SOAP 控制）→ HomeCast Relay →（重新发起 DLNA）→ 电视**。

我实现的 Go 模块：
- `ssdp`：SSDP 发现/响应（`ssdp:all`、精确 ST）
- `upnp`：SOAP 解析/构造（容错）
- `renderer`：DLNA 接收端（MediaRenderer 服务）
- `media`：本地媒体服务（HLS 代理/分片代理/转封装）
- `relay`：编排层（App 投屏 URL → 推给电视）
- `tv`：UPnP 电视控制（AVTransport / RenderingControl）
- `bili`：B站 playurl 客户端（拿流地址）

### 3.2 第二阶段：UI 重构（无关紧要但耗时）

把 UI 改成移动端友好的四页 SPA（首页 / 操作台 / 设备 / 日志），纯原生 JS + fetch 轮询，不用 htmx。投屏成功后自动进操作台。删掉"播放模式"选择（面向妈妈，全自动 `mode=auto`）。**这一步跟最终的病根无关，纯属项目基建。**

### 3.3 第三阶段：百度 App 扫不到设备

**现象**：百度 App 投屏列表里看不到 HomeCast Relay。

排查记录：
- SSDP 只响应精确 ST，加了 `ST: ssdp:all` 支持（`f52c857`）
- 百度识别设备"无效"：`description.xml` / SCPD 被严格校验。根因是 **AVTransport SCPD 引用了 9 个未定义的 `stateVariable`**，重写并补齐三个 SCPD（`71227eb`）
- SOAP 命名空间必须匹配服务类型，新增 `SoapResponseNS()`
- `description.xml` 补 `<dlna:X_DLNACAP>`，`presentationURL` 改 `/ui`
- 新增 `/event/` GENA 路由
- 修复非法 UUID（用 RFC4122 v4）

**结果**：百度 App 成功识别。**但这也不是最终病根**。

### 3.4 第四阶段：电视播放 m3u8 全 404（真·分片问题，已修）

**现象**：电视拿到了播放列表，但请求分片 `GET /m/0001355.ts` 全部 404。

排查记录（这是第一次真正接近"数据流"问题）：
- 电视请求 `/m/0001355.ts` → 404。电视解析 HLS 时把**相对路径** `0000000.ts` 拼成了 `/m/0001355.ts`（**丢掉了目录**）。
- 根因：HLS 分片的相对路径，电视按自己的 base 解析，丢了上游目录。
- 修复（`454ebed`）：**HLS 感知 proxy 模式** —— 用 **base64url 编码上游绝对 URL** 作为分片路径 `/m/<id>/seg/<b64>`。分片路径里直接带完整绝对 URL，彻底解决丢目录。
- 同时处理 `EXT-X-MAP`（fMP4 初始化段）、`EXT-X-KEY`（AES 密钥）、`EXT-X-MEDIA`、master playlist 子列表（`/pl/` 递归重写）。
- 播放列表识别**以 Content-Type 为准**（兼容抖音 URL 不带 `.m3u8` 后缀）。

端到端验证：播放列表 200、分片 200、`video/mp2t`、288204 字节、TS 魔数 `47 40 11 10` 正确、Range 206 精确 100 字节。**这个修好了，但用户实测发现"长时间播放还是会变卡"——说明分片 404 不是根因，还有更深的问题。**

### 3.5 第五阶段：通用性增强（防盗链 / 畸形 SOAP）

- **Referer 透传**（`4955238`）：盗版站/不知名站点的 CDN 校验 Referer，从 App 请求头透传（不能猜）。`guessHeaders` 按域名分流（B站/抖音/百度/优酷/爱奇艺/腾讯），认不出就不带。
- **SOAP 容错**：`sanitizeXML` 手动扫描转义裸 `&`（Go regexp 不支持负向前瞻），`isValidEntity` 校验实体；正则兜底提取 `CurrentURI`。
- **DASH 明确报错**：未实现就不假装支持。

### 3.6 第六阶段：电视拉流 4 秒后 404（Stop 误杀，已修但非根因）

**现象**：日志显示会话建立后电视正常拉流（多个 206），但 4 秒后突然 404。

```
22:30:56  新会话 ...223 建立，电视开始拉流（206）
22:31:00  B站 下发 Stop → 停止会话 ...223 → 电视 GET 404
```

排查记录：
- 根因：**B站 切换视频时先发 Stop 再发 Play，但 Stop 乱序晚到**，在新会话建立几秒内到达，`stopRelay()` 无条件杀当前会话 → 误杀正在播的新视频。
- 修复（`a790216`）：`Relay` 加 `startedAt`，App 发来的 Stop 若在会话建立后 6 秒内到达视为迟到的重复命令，**忽略**；UI 手动停止不受此限制，永远生效。
- 加了 3 个回归测试（迟到 Stop 不误杀 / UI 手动永远生效 / 超过窗口正常生效）。

**但用户实测：长时间播放还是变卡。这个也不是根因。**

### 3.7 第七阶段：PTS 重置器（大弯路，方向错）

用户反复强调"**音画一起变慢 + 爆破音 + 一直卡不恢复**"。我当时判断是 **PTS 时间戳漂移**（流的 PES 时间戳有累积误差，电视按 PTS 播就越播越慢）。

我写了一个**纯 Go 的 MPEG-TS PTS 重置器**（`pts.go`，零依赖零 ffmpeg）：
- 解析 188 字节 TS 包，找到 PES 头，重写 PTS/DTS 为连续值
- 检测帧率，按标准帧率精确累加
- 集成到 proxy 路径（`video/mp2t` 自动启用）
- 还加了**跨分片 EXTINF 累加**（每个分片时间戳起点 = 前面分片时长之和，抹平分片边界跳变）
- 修了一个 `io.Copy` 死循环 bug（不足 188 字节的分片返回 `(0,nil)`）

提交 `c15597b`，一堆单测全过（PTS 编解码、PES 解析、视频/音频重写、流式包装、短尾部不卡死、跨分片连续）。

**但这是弯路**。用户一句话点醒："**不是渐进变慢，是突然的爆破音 + 画面卡顿 + 一直卡不恢复**"。渐进 PTS 漂移是"越播越慢"，跟"突然崩坏 + 一直卡"对不上。而且用户明确："**流前期非常流畅，只是到期出问题**"——前期流畅说明流格式没问题，不是 PTS 漂移。

### 3.8 第八阶段：真相大白（"到期"这个词是金线索）

用户说："**现在的流非常流畅，只是到期出问题**"。"**到期**"两个字是突破口。

我查了项目代码：
- `media.Server` 的 HTTP client 是 `Timeout: 0`（无超时）
- relay 有 15 秒探测超时
- **`bili/playurl.go` 完全没处理 URL 的 `deadline`/过期** —— 拿了流 URL 就直接拿去代理，从不管它什么时候过期。

上网查证（搜索引擎 + B站逆向资料）：

> lazy-cv.com（专门逆向 B站 CDN）：
> **"Bilibili's segment URLs are signed, with a deadline (unix seconds) in the query. Pause a video, come back later, [it 403s]"**
> —— B站 的分片 URL 是签名 URL，query 里带 `deadline`（unix 秒）。暂停过会儿回来就 403 了。

> videohelp forum 标题直接：
> **"How to download stream with expiring tokens (url changes every 30 minutes)"**

**结论坐实**：

- B站 流 URL 是**签名 URL**，带 `deadline`（unix 秒时间戳）
- 有效期约 **30 分钟**
- **到期后 CDN 返回 403**
- 我们的代理还在拿**旧 URL** 拉分片 → 电视拉不到新数据 → **变卡 + 爆破音 + 一直卡不恢复**

### 3.9 网上查证：有没有人遇到同样问题？

确定是 URL 到期后，我又上网查证“B站投屏电视长时间播放卡顿/到期/403”是否有人公开遇到同样问题。

**结果：没有找到完全相同的公开案例。** 这个具体问题（投屏 30 分钟后 URL 到期变卡）少有人公开深究。

但找到了**官方佐证**，价值很高：

> **B站官方投屏帮助页**承认：
> “在电视上播放投屏内容的过程中，遇到**卡顿、花屏**等问题……可能是因为您的电视/智能盒子无法解析投屏视频，或是您所在的网络环境存在对投屏请求的阻挡。”
>
> **官方给的标准答案**：
> “建议在电视里下载安装**云视听小电视（哔哩哔哩TV版）**！……优先选择【我的小电视】这个设备进行投屏，可**大幅提高投屏成功率**。”

**为什么官方让你装 TV版？** 因为 TV版（云视听小电视）是 B站 自己写的播放器，**会像手机播放器一样自己管理 URL 续期**（定期重新拿带新 `deadline` 的分片）。而**普通 DLNA 投屏到第三方电视**：B站 App 把 URL 甩给电视后就不管了，第三方电视**不会续期** → 到期就卡。

**结论：这不是个例，是 B站 普通 DLNA 投屏的普遍缺陷。** 大多数用户要么没投到这么长，要么当网络问题算了，要么直接听官方建议装 TV版（TV版自己续期）。官方绕法就是“用会续期的播放器”，我们的中继要做的是**自己续期**，达到同样效果（还不用换播放器）。

## 四、最终结论（真相大白）

### 根因

**B站 CDN 的签名 URL 有约 30 分钟有效期，到期后 CDN 返回 403。投屏链路（无论直接投屏还是经中继）在 URL 到期后仍用旧地址拉流，电视拿不到数据，于是音画一起变卡、爆破音，且不恢复。**

### 为什么完美匹配所有症状

| 症状 | 解释 |
|------|------|
| 前期非常流畅 | URL 没过期，CDN 正常给数据 |
| ~15/20/30 分钟突然出问题 | URL 到期（约 30 分钟），CDN 开始 403 |
| 突然爆破音 + 画面卡顿 | 电视拉不到新分片，解码器缺数据 → 爆音卡顿 |
| 一直卡、不恢复 | URL 已**永久**失效，重拉也 403 |
| 只有 B站长视频 | 百度/抖音/盗版 URL 不过期或有效期更长，只有 B站 卡在 30 分钟 |
| 不是音画错位、是一起变慢 | 是**数据断了**（缺分片），不是时间戳错位 |

### 关键误区（复盘）

1. **分片 404**（3.4）—— 修了，但那是"电视解析路径丢目录"的**静态**问题，跟"到期"无关
2. **Stop 误杀**（3.6）—— 修了，但那是"切换视频"的**竞态**，跟"长时间播放"无关
3. **PTS 漂移**（3.7）—— **方向错了**。症状是"突发爆破音 + 一直卡"，不是"渐进变慢"。前期流畅证明流格式没问题。PTS 重置器**不该是主方案**
4. **真正的病根**是 **URL 到期（deadline → 403）**，属于**数据源过期**，不是流格式/时间戳问题
5. **为什么手机看 B站 不卡**：手机播放器是 DASH，**每几秒重拉 manifest 拿新 deadline**，自己续期。投屏链路没人续期，所以卡。B站 官方绕法（装 TV版）其实就是“用会续期的播放器”，中继做续期达到同样效果

## 五、解决方案（下一步）

在 URL `deadline` 到期前，**自动重新调 playurl 拿新 URL（续期），无缝切换**：

1. 解析 B站 流 URL 的 `deadline` 参数（unix 秒）→ 知道何时到期
2. 到期前 N 秒，重新调 `playurl` 拿**新** URL
3. 代理无缝切到新 URL（分片路径重定向到新 CDN），电视无感继续播
4. 这样流**永远不会到期**，也就不存在"播 30 分钟变卡"

这是**纯数据源续期**，跟转码、PTS、ffmpeg 都无关，符合项目"零 ffmpeg 零转码"的约束。

> **关键前提**：续期需要 `aid/cid`。投屏 URL 里只有 **cid**（`upgcxcode/52/00/<cid>/...`），**aid 不在 URL 里**。需要用 cid 向 B站 接口（`x/player/v2?cid=` 或 `view?cid=`）**反查 aid/bvid**，再调 playurl。另外登录状态续期需要 B站 登录凭证（cookie/access_key），可选配置，有则高清续期，无则降级保底（不断流）。

## 六、技术知识点汇总（CSDN 干货）

### 6.1 DLNA / UPnP AV
- 控制点（App）→ 媒体服务器/渲染器（DLNA 接收端）→ 目标渲染器（电视）
- 发现：SSDP（`M-SEARCH` / `NOTIFY`），ST 分精确类型和 `ssdp:all`
- 控制：SOAP over HTTP POST（AVTransport / RenderingControl）
- 事件：GENA（`SUBSCRIBE` / `NOTIFY`）

### 6.2 严格 DLNA 客户端（百度）的坑
- SCPD 里所有 `relatedStateVariable` 必须有对应 `stateVariable`，否则判定设备无效
- SOAP 命名空间必须匹配服务类型
- `description.xml` 需 `X_DLNACAP`、合法 UUID（RFC4122 v4）、`presentationURL`

### 6.3 HLS 分片代理的坑
- **相对路径丢目录**：电视按自己 base 解析分片相对路径会丢目录 → 用 base64url 编码**上游绝对 URL** 作分片路径，彻底解决
- 需处理 `EXT-X-MAP`（fMP4 初始化段）、`EXT-X-KEY`（AES 密钥）、`EXT-X-MEDIA`、master playlist 子列表
- 播放列表识别**以 Content-Type 为准**（抖音 URL 不带 `.m3u8` 后缀）

### 6.4 盗版站防盗链
- CDN 校验 `Referer`，必须透传 App 自带的 Referer（猜不出来）
- 探测时按候选 Referer 降级重试（App 自带 → 域名猜测 → 同源 origin → 无 Referer）
- 状态码语义：403/401 防盗链、404/410 失效、429 限流

### 6.5 MPEG-TS PTS 结构（顺带学的）
- TS 包 188 字节：sync `0x47` + PID + adaptation_field + payload
- PES 头：`00 00 01` + stream_id（`0xE0` 视频 / `0xC0` 音频）+ PTS/DTS（33 位，90kHz 时钟）
- PTS 编码：5 字节，marker 位恒 1

### 6.6 CDN 签名 URL（最终真相）
- **B站分片 URL 带 `deadline`（unix 秒），约 30 分钟到期，到期后 403**
- 签名 URL 是防盗链常见手段：query 里嵌过期时间戳 + 签名，边缘节点校验后才放行
- **播放器必须处理 URL 续期**，否则长时间播放会因 URL 过期而断流

## 七、坑与教训

1. **别过早下结论**：我先后修了"分片 404""Stop 误杀""PTS 漂移"，都以为是对的方向，但用户实测都无效。**真正的根因是 URL 到期**，得靠用户的关键观察（"前期流畅、到期才坏、只有B站"）+ 上网查证才锁定。
2. **"到期"这个词是金线索**：用户随口说的"到期"直接指向 URL 有效期/签名 token，比一堆技术分析都有用。
3. **PTS 漂移 vs 数据断流**：症状"渐进变慢" vs "突发爆破音+一直卡"是两个完全不同的病。前期流畅基本排除流格式问题，应优先怀疑**数据源过期/断流**。
4. **代理透传 403 的坑**：中继把上游 403 原样透传给电视，电视只能看到"拉不到数据"，不会告诉你"是 URL 过期"。中继应该**识别 403 并在到期前主动续期**。
5. **零 ffmpeg 约束**：转码/转封装方案（remux、PTS 重置）都因手机 CPU/无 ffmpeg 受限，而"URL 续期"是**纯逻辑**，零依赖，最适合这种中继场景。
